# PLAN: RAG-ассистент поддержки онлайн-кинотеатра «Фильмоскоп»

Документ описывает пошаговый маршрут разработки проекта от подготовки окружения до финальной диагностики качества. План синхронизирован со спецификацией `spec.md` и должен использоваться как рабочий трекер выполнения.

## Статусы

- `[ ]` — не начато.
- `[~]` — в работе.
- `[x]` — завершено.
- `[!]` — есть блокер или требуется решение.

## Целевые ориентиры проекта

- Итоговый `recall@5 >= 0.85` на запросах, где ответ есть в базе знаний.
- Итоговый `correctness >= 0.90` по всем 66 тестовым запросам.
- На `gap`-запросах система возвращает согласованный отказ и не выдумывает факты.
- Notebook выполняется сверху вниз без ручных изменений между ячейками.
- Все ключевые решения обоснованы числами, примерами или диагностикой ошибок.

## Принятая техническая рамка

- Основной фреймворк: LangChain.
- Vector store: Chroma, только как локальное прототипное хранилище.
- Embedding-модель по умолчанию: `intfloat/multilingual-e5-base`.
- LLM: локальный сервер Qwen3.5 на `http://localhost:8080/`.
- OpenAI-compatible base URL по умолчанию: `http://localhost:8080/v1`.
- Для локальной Qwen reasoning/thinking-модели все OpenAI-compatible chat-completion вызовы генератора и LLM-судьи должны передавать `chat_template_kwargs.enable_thinking=false`, иначе сервер может вернуть рассуждения в `message.reasoning_content` при пустом `message.content`.
- Reranker: `BAAI/bge-reranker-v2-m3`, включается при наличии ресурсов.
- Основной формат сдачи: Jupyter Notebook + модульный код в `src/`.
- Формат docstrings для функций: Google style на русском языке.
- Все комментарии, docstrings и описания функций в коде должны быть написаны на русском языке; английские имена переменных, функций, классов, импортов, моделей, API endpoints и технических параметров допускаются.
- `Settings` в `src/config.py` должен быть сгруппирован по тематическим dataclass-блокам: `runtime`, `data`, `llm`, `judge`, `embedding`, `chroma`, `chunking`, `retrieval`, `reranker`, `generation`; плоский перегруженный список параметров и плоские alias-свойства верхнего уровня в одном классе не допускаются.

## 1.3. Очистка и нормализация

**Статус:** `[~]`

### Корректировка подхода от 2026-11-20

Первая реализация пункта `1.3` признана недостаточной для HTML-документов: самописное извлечение текста через стандартный `HTMLParser` удаляет теги, но оставляет в корпусе шапку, меню, breadcrumbs, cookie-banner, связанные статьи, feedback-блоки и footer. Для RAG это загрязняет чанки повторяющейся обвязкой и ухудшает качество retrieval.

Принято решение заменить форматную очистку на библиотечный ingest-подход:

- HTML:
  - основной инструмент: `trafilatura` для выделения основного контента страницы;
  - fallback: `BeautifulSoup` + `lxml`, удаление служебных DOM-узлов и извлечение текста из `article`/`main`, если `trafilatura` не справилась.
- Markdown:
  - не очищать Markdown-разметку в plain text на этапе `1.3`;
  - сохранить Markdown как полезную структуру документа;
  - пометить Markdown-документы для следующего этапа и использовать Markdown-aware chunking на этапе `2.2`.
- Mojibake:
  - использовать `ftfy` как основной инструмент исправления уже испорченного текста;
  - принимать исправление только при уверенном улучшении диагностик;
  - не пытаться автоматически восстанавливать символ `�`, если исходные байты уже потеряны.
- Кодировки:
  - `charset-normalizer` не добавлять в текущий MVP, так как входом является уже декодированный JSON, а не набор raw TXT-байтов неизвестной кодировки.
- Unicode/whitespace:
  - использовать `unicodedata` и минимальные регулярные выражения только для схлопывания пробелов, удаления управляющих символов, дефенизации и диагностики остаточного мусора.

### Задачи

- Добавить зависимость `trafilatura` для HTML content extraction.
- Добавить зависимость `ftfy` для исправления mojibake в уже декодированных строках.
- Проверить, что `beautifulsoup4` и `lxml` зафиксированы и используются как fallback для HTML.
- Переписать очистку HTML: сначала `trafilatura`, затем fallback на `BeautifulSoup` + `lxml`.
- Убрать самописный HTML parsing через `HTMLParser` как основной путь очистки.
- Не очищать Markdown в plain text на этапе `1.3`; сохранить структуру и пометить такие документы для Markdown-aware chunking.
- Убрать целевой показатель `markdown_documents: 29 → 0`; наличие Markdown-документов после этапа `1.3` допустимо и ожидаемо.
- Исправить mojibake через `ftfy`, если диагностика уверенно показывает улучшение.
- Нормализовать пробелы и переносы строк.
- Удалить или пометить явно нерелевантные документы только при наличии обоснования.
- Не удалять данные, которые можно восстановить.

### Критерии готовности

- Есть очищенный корпус.
- Есть сравнение метрик качества «было → стало».
- Есть примеры конкретных документов до и после очистки.
