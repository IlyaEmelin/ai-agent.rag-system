# RAG-ассистент поддержки онлайн-кинотеатра «Фильмоскоп»

## Краткое описание

Проект представляет собой воспроизводимый прототип RAG-системы для службы поддержки онлайн-кинотеатра «Фильмоскоп». Ассистент должен отвечать на вопросы пользователей по базе знаний, находить релевантные разделы, формировать заземлённый ответ и честно отказываться отвечать, если нужных сведений в базе нет.

Реализация выполняется на базе LangChain. Основной формат сдачи — Jupyter Notebook, дополненный модульным кодом в `src/` для очистки данных, чанкинга, retrieval, генерации, оценки и диагностики.

## Проблема и цель

### Проблема

Служба поддержки «Фильмоскопа» получает много однотипных вопросов о подписках, оплате, устройствах, ошибках воспроизведения, аккаунтах, профилях, функциях и контенте. Ранее команда пробовала подключить языковую модель без базы знаний, но модель называла несуществующие тарифы и обещала акции, которых сервис не проводил.

### Цель

Собрать RAG-пайплайн, который:

- отвечает только на основании базы знаний «Фильмоскопа»;
- возвращает согласованную фразу отказа, если ответа в базе нет;
- имеет измеримое качество по retrieval- и generation-метрикам;
- содержит диагностику ошибок и инженерный вердикт о готовности к пилоту.

## Пользователи и роли

- **Пользователь онлайн-кинотеатра** — задаёт вопрос о сервисе и ожидает точный ответ.
- **Оператор поддержки** — потенциально использует ассистента как источник черновика ответа.
- **Инженер/аналитик RAG-системы** — запускает notebook, анализирует метрики, ошибки и принимает решение о готовности к пилоту.
- **Ревьюер проекта** — проверяет воспроизводимость, полноту этапов, обоснованность решений и качество анализа.

## Основные сценарии

### Сценарий 1. Ответ на вопрос, покрытый базой знаний

1. Пользователь задаёт вопрос.
2. Система преобразует вопрос в embedding.
3. Retrieval-пайплайн ищет релевантные чанки в Chroma.
4. При необходимости результаты улучшаются гибридным поиском и/или reranking.
5. Генератор получает вопрос и найденный контекст.
6. Генератор возвращает краткий ответ, основанный на контексте.

### Сценарий 2. Вопрос без ответа в базе знаний

1. Пользователь задаёт вопрос, относящийся к `gap`-типу.
2. Retrieval не находит достаточно надёжного контекста или найденный контекст не содержит ответа.
3. Генератор возвращает согласованную фразу отказа без выдуманных фактов.

### Сценарий 3. Диагностика качества

1. Notebook прогоняет все 66 тестовых запросов.
2. Система считает retrieval-метрики и generation-метрики.
3. Для худших запросов выводятся вопрос, gold, найденные чанки, ответ и оценки judge.
4. Выполняется прогон с золотым контекстом.
5. Формируется итоговый вердикт и рекомендации.

## Объём первой версии (MVP)

### Входит в MVP

- Загрузка `filmoskop_kb.json`.
- Аудит корпуса: категории, форматы, длины, мусорные символы, остатки разметки, подозрительные документы, дубли.
- Очистка и нормализация корпуса с отчётом «было → стало».
- Две стратегии чанкинга и сравнение по retrieval-метрикам.
- Embedding-модель `intfloat/multilingual-e5-base`, если хватает ресурсов текущей машины.
- Chroma как локальное векторное хранилище для прототипа.
- Dense retrieval baseline.
- Retrieval-метрики: `precision@5`, `recall@5`, `MRR`, recall-кривая для `K in {1, 3, 5, 10, 20}`.
- Фильтрация по метаданным минимум на одном примере, например по категории «Подписка и оплата».
- Диагностика слабых запросов.
- Улучшение retrieval через гибридный поиск, RRF и/или reranker.
- Reranker, вынесенный в настройки: `BAAI/bge-reranker-v2-m3`.
- Генерация ответов через локальный LLM-сервер `http://localhost:8080/` с моделью Qwen3.5.
- Все имена моделей и основные параметры вынесены в `.env` и задокументированы в `.env.example`.
- LLM-as-judge для `faithfulness`, `answer relevance`, `correctness`.
- Прогон всех 66 тестовых запросов.
- Разбивка метрик по типам запросов: `exact`, `semantic`, `multi`, `gap`.
- Прогон с золотым контекстом.
- Финальный инженерный вердикт о готовности к пилоту.
- Google-style docstrings у функций в `src/`.

### Не входит в MVP

- Production API-сервис.
- Пользовательский web-интерфейс.
- Авторизация пользователей.
- Интеграция с реальной системой поддержки.
- Мониторинг production-трафика.
- Автоматическое обновление базы знаний по расписанию.
- Распределённое хранение индексов.
- Chroma как production-хранилище. В этом проекте Chroma используется только для локального прототипа и экспериментов в notebook.

## Функциональные требования

### Данные и очистка

- Система должна загружать датасет из пути, заданного в настройках.
- Система должна разделять `docs` и `queries`.
- Система должна сохранять `doc_id`, `title`, `category`, `format` и очищенный текст каждого раздела.
- Система должна обнаруживать и показывать минимум следующие проблемы данных:
  - остатки HTML/Markdown-разметки;
  - mojibake/ошибки кодировки;
  - мусорные символы;
  - подозрительно короткие и подозрительно длинные документы;
  - дубли или почти дубли;
  - архивные/нерелевантные документы, если они выявляются эвристиками и ручным анализом.
- Система должна показывать примеры документов до и после очистки.

### Чанкинг

- Система должна реализовать две стратегии чанкинга.
- Для каждой стратегии должны быть построены чанки с метаданными:
  - `doc_id`;
  - `title`;
  - `category`;
  - `format`;
  - `chunk_id`;
  - `chunk_index`;
  - параметры стратегии чанкинга.
- Выбранная стратегия должна быть обоснована метриками и ручным просмотром чанков.

### Embeddings и vector store

- Система должна использовать embedding-модель из `.env`.
- Значение по умолчанию: `intfloat/multilingual-e5-base`.
- Если ресурсов локальной машины не хватает, допустимо заменить embedding-модель через `.env`, зафиксировав это в notebook и итоговом выводе.
- Система должна создавать Chroma collection для каждой сравниваемой стратегии чанкинга или явно пересоздавать collection между экспериментами.
- Chroma используется как прототипное локальное хранилище, а не как production-решение.

### Retrieval

- Система должна выполнять dense retrieval через Chroma.
- Система должна возвращать top-K чанков с метаданными и score.
- Система должна поддерживать порог отсечения по similarity/distance score.
- Порог должен быть выбран на основании распределения score и влияния на качество.
- Retrieval-метрики считаются только для запросов с непустым `relevant_docs`.
- При расчёте метрик результаты на уровне чанков должны агрегироваться до уникальных `doc_id`.
- Система должна поддерживать фильтрацию по метаданным минимум для категории.

### Улучшение retrieval

- Система должна диагностировать запросы с низким recall/MRR.
- Система должна реализовать минимум один метод улучшения retrieval:
  - гибридный поиск Dense + BM25;
  - RRF для слияния результатов;
  - reranker;
  - query expansion;
  - HyDE.
- Базовый рекомендуемый MVP-подход: Dense retrieval через Chroma + BM25 + RRF; reranker добавить как улучшение при наличии ресурсов.
- Сравнение «до → после» должно выполняться на одном и том же тестовом наборе и одних и тех же метриках.

### Генерация

- Система должна подключаться к локальному LLM-серверу через настройки `.env`.
- Основной endpoint: `http://localhost:8080/`.
- Для OpenAI-compatible клиента рекомендуется использовать base URL с суффиксом `/v1`, если сервер его поддерживает: `http://localhost:8080/v1`.
- Имя chat-модели должно задаваться через `.env`.
- Температура генерации должна быть `0`.
- Prompt должен явно запрещать выдумывать факты вне контекста.
- Prompt должен содержать инструкцию вернуть согласованную фразу отказа, если ответа нет в контексте.
- Контекст и вопрос должны быть разделены в prompt.

### Оценка генерации

- Система должна реализовать LLM-судью для:
  - `faithfulness`;
  - `answer_relevance`;
  - `correctness`.
- `correctness` должна быть бинарной сверкой ответа с `gold`.
- Для `gap`-запросов корректным ответом считается согласованный отказ без добавления неподтверждённых фактов.
- Судья должен работать при `temperature=0`.
- Prompt судьи должен требовать структурированный ответ, пригодный для парсинга.

## Нефункциональные требования

- Notebook должен выполняться сверху вниз без ручных изменений между ячейками.
- Все основные параметры должны быть вынесены в `.env`.
- В репозитории должен быть `.env.example` без секретов.
- Реальный `.env` не должен попадать в git.
- Случайность должна быть зафиксирована через seed, где это возможно.
- Функции в `src/` должны иметь Google-style docstrings.
- Код должен быть модульным: notebook оркестрирует этапы, а повторно используемая логика находится в `src/`.
- Метрики должны быть воспроизводимыми на одном и том же датасете и настройках.
- Все существенные инженерные решения должны быть объяснены в markdown-ячейках notebook.
- Проект должен запускаться локально, а затем переноситься для тестового прогона на удалённую машину.

## Данные и сущности

### Dataset

Источник данных:

```bash
wget https://code.s3.yandex.net/ai-engineer/Итоговый_проект_спринт2/filmoskop_kb.json -O filmoskop_kb.json
```

Локальный путь по умолчанию задаётся в `.env`:

```text
DATASET_PATH=filmoskop_kb.json
```

### Document

Поля исходного раздела базы знаний:

- `doc_id` — идентификатор раздела;
- `title` — заголовок;
- `category` — категория;
- `format` — формат выгрузки: `html`, `markdown` или `text`;
- `raw` — исходный текст раздела.

### Query

Поля тестового запроса:

- `query` — вопрос пользователя;
- `kind` — тип запроса: `exact`, `semantic`, `multi`, `gap`;
- `relevant_docs` — список релевантных разделов;
- `gold` — эталонный факт или эталон отказа.

### Chunk

Поля чанка:

- `page_content` — текст чанка;
- `metadata.doc_id`;
- `metadata.title`;
- `metadata.category`;
- `metadata.format`;
- `metadata.chunk_id`;
- `metadata.chunk_index`;
- `metadata.chunking_strategy`.

## Выбранная техническая реализация

Выбран вариант B: **LangChain + Chroma + гибридная диагностика**.

### Основные компоненты

- **LangChain** — orchestration, `Document`, text splitters, prompts, model wrappers.
- **Chroma** — локальное векторное хранилище для прототипа.
- **Embedding model** — `intfloat/multilingual-e5-base` по умолчанию.
- **LLM** — локальный сервер Qwen3.5 на `http://localhost:8080/`, имя модели задаётся через `.env`.
- **ChatModel wrapper** — предпочтительно OpenAI-compatible клиент через `langchain-openai.ChatOpenAI`, если локальный сервер поддерживает `/v1/chat/completions`.
- **Альтернативы ChatModel**:
  - LangChain wrapper поверх OpenAI-compatible API локального сервера;
  - кастомный LangChain `BaseChatModel`, если API сервера отличается от OpenAI-compatible формата;
  - `HuggingFacePipeline` как fallback для прямого локального запуска модели, если сервер недоступен.
- **BM25** — sparse retrieval для гибридного поиска.
- **RRF** — слияние dense и sparse результатов.
- **Reranker** — `BAAI/bge-reranker-v2-m3`.
- **LLM-as-judge** — тот же локальный LLM-сервер или отдельная judge-модель из `.env`.

### Почему Chroma

Chroma выбран, потому что:

- хорошо интегрируется с LangChain;
- удобен для notebook-экспериментов;
- поддерживает хранение метаданных чанков;
- позволяет показать фильтрацию по метаданным;
- может локально сохранять collection на диск.

Ограничение: в рамках этого проекта Chroma рассматривается только как **прототипное локальное хранилище**. Для production-пилота выбор vector store нужно пересмотреть с учётом требований к нагрузке, отказоустойчивости, обновлению индексов, мониторингу, резервному копированию и разграничению доступа. На больших объёмах или при необходимости production-инфраструктуры кандидатом будет Qdrant или другой специализированный vector DB.

## Ограничения и допущения

- Проект разрабатывается локально.
- Тестовый прогон выполняется на удалённой машине.
- Локальный LLM-сервер доступен по адресу `http://localhost:8080/`.
- Предполагается, что сервер предоставляет OpenAI-compatible API по адресу `http://localhost:8080/v1`. Если это не так, потребуется кастомный клиент или wrapper.
- Название Qwen3.5-модели задаётся через `.env`, потому что конкретный model id зависит от локального сервера.
- Embedding-модель `intfloat/multilingual-e5-base` используется, если хватает ресурсов текущей машины.
- Reranker включается только если хватает CPU/GPU/RAM и приемлема задержка.
- Chroma используется только для прототипа.
- Все внешние учебные репозитории рассматриваются как источник подходов и кода для адаптации, а не как готовая неизменяемая реализация.

## Критерии готовности

### Retrieval

- Для итогового retrieval на запросах с ответом в базе рассчитаны:
  - `precision@5`;
  - `recall@5`;
  - `MRR`;
  - recall@K для `K in {1, 3, 5, 10, 20}`.
- Целевой ориентир: `recall@5 >= 0.85`.
- Есть сравнение baseline и улучшенного retrieval.
- Есть диагностика запросов с низкими метриками.

### Generation

- Для всех 66 запросов получены ответы.
- Для `gap`-запросов система не выдумывает факты и возвращает согласованный отказ.
- Для всех 66 запросов рассчитана `correctness`.
- Целевой ориентир: `correctness >= 0.90`.

### Notebook и отчётность

- Notebook разделён на 6 этапов из задания.
- Код выполняется сверху вниз.
- Результаты выполнения ячеек сохранены.
- В конце каждого этапа есть краткий вывод:
  - что сделали;
  - что получили;
  - какое решение приняли;
  - почему приняли именно его.
- В финале есть инженерный вердикт о готовности к пилоту и минимум 3 конкретные рекомендации по улучшению.

## Открытые вопросы

1. Точный OpenAI-compatible endpoint локального сервера Qwen3.5 нужно проверить: `http://localhost:8080/v1` или другой путь.
2. Точный model id Qwen3.5 нужно сверить с ответом endpoint `/v1/models` или настройками сервера.
3. Нужно проверить, хватает ли ресурсов локальной машины для `intfloat/multilingual-e5-base` и выбранного reranker.
4. Нужно определить, какие конкретные фрагменты кода из учебных репозиториев будут адаптированы после просмотра их структуры.
5. Нужно выбрать финальную стратегию улучшения retrieval после baseline-диагностики: Dense + BM25 + RRF, reranker, query expansion, HyDE или комбинация.
